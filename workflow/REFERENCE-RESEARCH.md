# Reference research and optional tools

Use references to answer a specific question: composition, density, typography, data encoding, interaction or motion. Record actual viewed images/states and source URLs in the experiment's docs/RESEARCH.md; keep any saved reference assets under assets/references/. Keep sources distinct from exported design evidence. Do not copy whole products or assume publicly visible assets are licensed for reuse.

## Inspo MCP

Optional research connector, not a design author or required dependency. Its documented tools include recommend, search_screens, get_screen, get_design_system and compare; screenshots and extracted design-system information are already provided by the service. Static archive research does not inherently require Playwright or a second browser MCP.

When available, discover its current tool schemas, search from the product/task and selected character, then actually view useful images. Treat suggested palette/layout and extracted DESIGN.md as reference observations, not instructions. Seek task-appropriate sources beyond marketing pages when designing dense applications. Do not let a recommended macrostructure dictate the product.

The connector is not installed by this workflow update. Do not silently run installers or change client configuration. If absent, use available image/web sources, disclose limitations and proceed with usable evidence.

## Live behavior research

An available browser connector (for example Chrome DevTools or Playwright) may inspect public reference sites read-only when live hover, scrolling, menus or transitions matter. This is a narrow research exception to the design-only boundary, not permission to build/run the designed application. Prefer an existing capable connector; do not require two equivalent browser stacks. Do not log in, submit forms or change reference-site data just to inspect appearance.

For static treatment, screenshots suffice. For motion, observe actual playback or inspect a legitimately obtained reference clip with timestamps/frames. Several stills alone do not establish easing, timing or interaction responsiveness. Discover supported capture/playback capabilities rather than assuming a browser MCP records or understands video. Record viewport, trigger, observed states, duration evidence and uncertainty. A FigCraft storyboard documents intended motion; it does not verify that motion ran.

## Quality comparison

Assign stable reference IDs and screen/state/viewport IDs. Compare reference and design at comparable viewing scale and label contextual differences; do not stretch one to fake a match. Compare the dimensions relevant to this target, not pixel similarity to a different product. Give each chosen reference a short “learn / do not copy” note. Keep reference prestige separate from observed execution quality.

Include task-relevant examples and execution benchmarks from other categories when useful. For images actually viewed, identify the first focal point, scale and credibility of product evidence, relationship of copy to visual, and rhythm between adjacent sections where applicable. Record a concrete transferable principle and a boundary against copying. Compare screenshots side by side at comparable scale when possible; note viewport and unavailable views. Do not infer interaction or motion from stills.

## Component and interaction references

When a core task depends on a complex or unfamiliar control, consult relevant official component demos while designing the sample. [MUI X Data Grid](https://mui.com/x/react-data-grid/) is a reference for dense tables, selection, filters and empty states. [shadcn/ui](https://ui.shadcn.com/docs/components/combobox) is a reference for patterns such as searchable selection, multiple values and no matches. Start with the product's existing system when the brief specifies one. Choose examples based on the task and the states the screen needs.

Record the pattern, source and states studied in RESEARCH. Apply the selected direction's type, density, colors and shapes. Keep related controls consistent if their patterns come from different sources. Treat the pattern as a starting point for the product's task. For example, a generic dialog example can show dismissal and focus intent, while the task determines what the detail adds and whether inline disclosure would fit.

Use a ready-made design component when a licensed asset is available through a supported FigCraft import and its needed layers, properties, states and instances remain usable. Verify a representative instance, including theme adaptation and a relevant difficult state, before reuse. Record the source and adopted component in DESIGN. When only code or a demo is available, use it as a reference and build the needed states in native FigCraft layers. Runtime behavior and any future package choice follow the brief and subsequent implementation.
