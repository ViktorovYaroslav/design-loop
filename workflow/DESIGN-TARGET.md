# Design target — turn an idea into an observable outcome

The user supplies an idea, not an art-direction specification. The designer authors a short experiment-local docs/TARGET.md after scope inspection and style-character selection, before drawing. Infer routine decisions; ask only when a missing fact materially changes the product. Label assumptions. Do not ask the user to choose every font, proportion or component.

## Target contents

- Audience, situation and main job; 3–5 tasks linked to TASK-WALKTHROUGH.
- Required screen/state/viewport pairs, their first-visible content and the decision/action each enables. Keep these IDs stable for before/after comparison.
- Visual ambition: selected character, intended first focus, supporting hierarchy, distinctive device and what must remain quiet. Translate adjectives into visible choices.
- Reference roles: style inspiration, execution-quality benchmark, or task/data example. Name the dimension learned from each; a quality benchmark does not authorize copying its layout or branding.
- Observable completion conditions for task clarity, composition, type, graphics, states and craft. Separate must-haves from exploratory preferences and implementation-stage checks.
- Explicit exclusions and unresolved assumptions. Keep the original deliverables visible as the design develops.

Example from a logistics idea: “A dispatcher can identify the highest-risk hub in the overview and reach the affected shipment detail. Risk must be more salient than healthy connections. A dense table remains legible at the smaller working viewport. The same accent/shape language carries across overview and detail.” These are design targets, not claims of measured user success.

Write one compact document, not another long PRD. Its initial version is a hypothesis. Direction choice and checkpoint-2 feedback refine it; they do not silently remove original requirements. Present a brief target summary with the normal direction presentation; no extra mandatory approval gate.

## Calibrate expectations with evidence

Record user feedback in their exact words and language in docs/ROUNDS.md, alongside the inspected revision. Preserve a rating as subjective feedback, never as a measured percentage of completion. Ask for a concrete example or show two alternatives only when the feedback is too ambiguous to act on. The user need not supply the solution.

Translate feedback into 1–3 visible gaps and proposed corrections. Compare the same screen/state/viewport before and after. Separate visual character, execution, task clarity and system completeness; a high average cannot cancel a serious defect. Do not apply a fixed numeric offset to future scores or claim 99% reference matching without a defined measurement.

The author sees feedback; fresh independent reviewers receive the resulting factual requirements, but not previous ratings, praise or a list of expected defects. TARGET complements BRIEF, DIRECTION and ACCEPTANCE rather than replacing them.

## Round record

Keep docs/ROUNDS.md concise: revision/evidence → user feedback or observed gap → primary focus → change → actual check/result → remaining issue or regression. Record tool checks separately from visual judgment. Preserve the best known evidence revision before substantial changes; restore/revise a regression through supported save/version operations, never by overwriting another experiment. Use existing FLOW review limits; there is no mandatory hours/token quota or endless refinement loop.
